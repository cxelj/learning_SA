# Нереляционные базы данных (NoSQL)

> Альтернатива реляционным БД: нет строгих таблиц, другие модели данных, ориентированы на масштабирование и скорость.

## Что такое NoSQL

**NoSQL** (Not Only SQL) — общее название нереляционных БД. Вместо таблиц-строк-JOIN'ов — ключ-значение, документы, графы, wide-column.

## Виды NoSQL БД

### 1. Key-Value (ключ-значение)

Хранит пары ключ → значение.

```
"user:42"    → { "name": "Иван", "email": "..." }
"session:99" → { "user_id": 42, "expires": "..." }
```

| Пример | Применение |
|--------|-----------|
| **Redis** | Кэш, сессии, рейтинги, очереди, хранение счётчиков |
| **Memcached** | Простой кэш |
| **DynamoDB** (AWS) | Высоконагруженные key-value в облаке |

### 2. Document (документные)

Хранят документы (JSON-подобные) с гибкой схемой.

```json
{
  "_id": "5f8c...",
  "user": {
    "name": "Иван",
    "email": "ivan@example.com",
    "preferences": { "theme": "dark", "language": "ru" }
  },
  "orders": [ ... ],
  "tags": ["vip", "loyal"]
}
```

Гибкая структура: каждый документ может иметь свои поля. Вложенность вместо JOIN'ов.

| Пример | Применение |
|--------|-----------|
| **MongoDB** | Контент, каталоги, JSON-данные с переменной структурой |
| **CouchDB**, **Firestore** | Мобильные приложения, синхронизация |

### 3. Wide-Column (широкие колонки)

Таблицы, но колонки могут различаться у разных строк. Оптимизированы для огромных объёмов и времени.

```
Ряды:   user_id | 2024-01 | 2024-02 | 2024-03 ...
7f3a... |  10     |  15     |  22
9b11... |  (нет)  |  7      |  18
```

| Пример | Применение |
|--------|-----------|
| **Cassandra** | Временные ряды, сенсоры, логи, огромные объёмы |
| **HBase** | Big Data (Hadoop экосистема) |
| **ScyllaDB** | Высокопроизводительная Cassandra-совместимая |

### 4. Graph (графовые)

Данные — узлы и рёбра (связи). Идеальны для анализа связей.

```
(Пользователь:Иван) —[подписан на]→ (Канал:Технологии)
    │                                     │
    └──[друг]→ (Пользователь:Пётр) ←──────┘
```

| Пример | Применение |
|--------|-----------|
| **Neo4j** | Соцсети, рекомендации, анализ мошенничества |

### 5. Поисковые (Search)

Оптимизированы для полнотекстового поиска.

| Пример | Применение |
|--------|-----------|
| **Elasticsearch** | Поиск по тексту, логи (ELK), аналитика |
| **OpenSearch** | Открытый форк Elasticsearch |

## Сравнительная таблица

| Тип | Модель | Гибкость | Масштаб | Скорость | Плюсы | Минусы |
|-----|--------|----------|---------|----------|-------|--------|
| Key-Value | пары | Низкая | Отличный | Отличная | Простота, скорость | Нет сложных запросов |
| Document | JSON-документы | Высокая | Хороший | Хорошая | Гибкая схема, похоже на код | Нет JOIN'ов, слабые relationship |
| Wide-Column | таблицы с колонками | Средняя | Отличный | Хорошая | Огромные объёмы | Сложные операции обновления |
| Graph | узлы и рёбра | Высокая | Средний | Хорошая (по связям) | Анализ связей | Специфичный кейс |
| Search | инвертированный индекс | Низкая | Отличный | Хорошая | Полнотекстовый поиск | Специфичен |

## Redis — как пример (Key-Value)

**Redis** — in-memory БД (данные в RAM), где операции выполняются за микросекунды.

### Типы данных Redis

| Тип | Пример | Применение |
|-----|--------|-----------|
| String | `SET user:42 "Иван"` | Кэш, счётчики, лимиты |
| Hash | `HSET user:42 name Иван age 30` | Объекты |
| List | `LPUSH queue:emails "mail@x.com"` | Очереди |
| Set | `SADD online_users u1 u2` | Множества (уникальные) |
| Sorted Set | `ZADD leaderboard 100 u1` | Рейтинги, лидерборды |

### Примеры команд

```bash
# Кэш
SET cache:order:77 '{"total": 1500}' EX 3600   # на 1 час
GET cache:order:77

# Счётчик
INCR visits:today

# Очередь
LPUSH job:queue "process-file"
BRPOP job:queue 5

# Лидерборд
ZADD rating 1000 user:1
ZADD rating 800 user:2
ZREVRANGE rating 0 9    # топ-10
```

### Когда Redis

✅ Кэширование (несколько ms вместо 20-50ms по БД)  
✅ Сессии пользователей  
✅ Rate limiting (лимиты запросов)  
✅ Очереди (job queue)  
✅ Рейтинги/лидерборды  
✅ Pub/Sub для событий  

### Когда НЕ Redis

❌ Как **единственное** хранилище (in-memory — данные теряются при перезапуске)  
❌ Сложные выборки и агрегации (не его профиль)  
❌ ACID-требования  
❌ Данные больше, чем помещается в RAM  

> Redis используют **рядом с** основной БД (PostgreSQL/MongoDB) — как быстрый слой.

## Как выбрать NoSQL — конкретные сценарии

| Задача | БД | Почему |
|--------|-----|--------|
| Кэш для API | **Redis** | Микросекунды, in-memory |
| Каталог товаров с разными свойствами | **MongoDB** | Гибкая схема (разные товары — разные поля) |
| Логи и сенсоры (млн записей/день) | **Cassandra** | Широкие колонки, время — первичный ключ |
| Рекомендации друзей | **Neo4j** | Поиск по связям — O(1) по рёбрам |
| Поиск по документам | **Elasticsearch** | Полнотекстовый поиск |
| Онлайн-магазин (заказы, платежи) | **PostgreSQL** | Транзакции и целостность важнее |

## SQL vs NoSQL — краткая таблица

| Критерий | SQL (реляционные) | NoSQL |
|----------|-------------------|-------|
| Схема | Строгая (фиксированная) | Гибкая / отсутствует |
| Связи | Через JOIN (FK) | Вложенность / денормализация |
| Транзакции | ACID | BASE (в основном) |
| Масштабирование | Вертикальное (обычно) | Горизонтальное |
| Запросы | SQL — мощный и стандартный | Специфичны каждой БД |
| Целостность | Гарантируется | Ответственность приложения |

> **BASE** (в противовес ACID): Basically Available, Soft state, Eventual consistency — «по сути доступна, мягкое состояние, конечная согласованность».

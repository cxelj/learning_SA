# GraphQL

> Язык запросов к API: клиент сам задаёт структуру ответа. Альтернатива REST от Facebook (2015).

## Проблема REST, которую решает GraphQL

**REST: over-fetching и under-fetching**

```
REST:
GET /api/users/42            → возвращает ВСЕ поля (даже ненужные)  = over-fetching
GET /api/users/42/orders     → ещё один запрос                       = under-fetching

Чтобы собрать профиль + его заказы: 2-3 запроса и лишние данные.
```

**GraphQL: один запрос, только нужные поля**

```graphql
query {
  user(id: 42) {
    name
    email
    orders {
      total
      status
    }
  }
}
```

Один запрос → все данные, только запрошенные поля.

## Как работает GraphQL

```
Клиент ── POST /graphql ──► Сервер
        ◄─────────────────
  { query: "..." }       { "data": {...} или "errors": [...] }
```

Всё через один endpoint (обычно `/graphql`). Типы и операции описаны в **схеме**.

## Основные концепции

### 1. Schema (схема) — контракт API

```graphql
type Query {          # операции чтения
  user(id: ID!): User
  products(category: String): [Product!]!
}

type Mutation {       # операции изменения
  createOrder(input: CreateOrderInput!): Order!
}

type User {
  id: ID!
  name: String!
  email: String!
  orders: [Order!]
}

type Order {
  id: ID!
  total: Float!
  status: String!
}
```

### 2. Query — чтение

```graphql
query {
  products(category: "food") {
    id
    name
    price
  }
}
```

### 3. Mutation — изменение

```graphql
mutation {
  createOrder(
    input: {
      productId: 42
      quantity: 2
    }
  ) {
    id
    status
    total
  }
}
```

### 4. Subscription — подписка (реалтайм через WebSocket)

```graphql
subscription {
  orderUpdated {
    id
    status
  }
}
```

## Типы и модификаторы

| Синтаксис | Значение |
|-----------|----------|
| `String!` | Обязательное (не NULL) |
| `[Order]` | Список заказов |
| `[Order!]!` | Список, не NULL, элементы не NULL |
| `ID` | Уникальный идентификатор |

## Граф связей — главная фишка

Данные — **граф**, клиент «путешествует» по нему:

```graphql
query {
  user(id: 42) {
    name
    orders {
      items {
        product {
          name
          category {
            name
          }
        }
      }
    }
  }
}
```

## GraphQL vs REST

| Критерий | REST | GraphQL |
|----------|------|---------|
| Конечные точки | Множество (на ресурс) | Один `/graphql` |
| Данные в ответе | Фиксированные поля | Клиент выбирает |
| Кол-во запросов | Может быть много | Обычно один |
| Версионирование | /v1/, /v2/ | Эволюция схемы (deprecation) |
| Кэширование | ✅ Встроенное HTTP-cache | ❌ Сложнее |
| Сложность сервера | Проще | Сложнее (резолверы) |
| Мониторинг | Проще | Сложнее |
| Гибкость клиента | Малая | Высокая |
| Типизация | Слабая (JSON) | Строгая (схема) |
| Over-fetching | Есть | Нет |
| Когда применять | Стандартные/публичные API | Сложные клиенты, агрегация, mobile |

## Риски GraphQL (важно знать!)

### 1. N+1 проблема
Запрос глубоко по графу может вызвать **много запросов в БД**.

```graphql
# 1 пользователь → 100 заказов → у каждого товар
# = 1 запрос за пользователем + 100 за заказами + ...
# Проблема! Решение: DataLoader / batch запросы
```

### 2. Сложные запросы (запрос слишком глубокий/дорогой)

```
Открытый endpoint может быть атакован вложенными запросами (циклы):
user { orders { user { orders { user ... } } } }

Решение: лимиты глубины (depth limit), стоимость запросов, rate limit.
```

### 3. Кэширование сложнее
POST + динамическая структура ≠ HTTP GET cache. Решение: Apollo Client, кэш на уровне приложения.

## Когда применять GraphQL

**Применять:**
- Мобильные приложения (разные объёмы данных на разных экранах)
- Агрегация данных из нескольких источников
- Сложные клиенты с множеством экранов/виджетов
- Когда команда фронта хочет гибкость

**НЕ применять:**
- Простые CRUD API (оверкилл)
- Публичные API для внешних разработчиков (стандарт — REST)
- Внутренние простые сервис-to-сервис (лучше gRPC)
- Когда нужен простой HTTP-caching

# Микросервисы

> Архитектурный стиль: приложение разбивается на **небольшие независимые сервисы**, каждый из которых отвечает за свою бизнес-функцию.

## Монолит vs Микросервисы

### Монолит
Всё приложение — одна программа:
- Один код, один деплой, одна база данных
- Просто в начале, сложно в масштабе

```
┌─────────────────────────────────────┐
│            MONOLITH APP              │
│  ┌──────────┬──────────┬──────────┐  │
│  │ Auth     │ Orders   │ Payments │  │
│  └──────────┴──────────┴──────────┘  │
│  ┌────────────────────────────────┐  │
│  │        ONE DATABASE             │  │
│  └────────────────────────────────┘  │
└─────────────────────────────────────┘
```

### Микросервисы
Приложение — набор независимых сервисов:
- Каждый сервис: свой код, свой деплой, свою БД
- Сложно настраивать, зато масштабируется и не падает целиком

```
     ┌──────────┐   ┌──────────┐   ┌──────────┐
     │  Auth    │   │  Orders  │   │ Payments │
     │ service  │   │ service  │   │ service  │
     └────┬─────┘   └────┬─────┘   └────┬─────┘
          │              │              │
        БД auth        БД orders      БД payments
          │              │              │
          └──────────────┼──────────────┘
                         ▼
                API Gateway (единая точка входа)
                         │
                      Клиент
```

## Характеристики микросервисов

| Характеристика | Описание |
|----------------|----------|
| **Независимость** | Сервисы разрабатываются, деплоятся, масштабируются отдельно |
| **Один бизнес-домен** | Каждый сервис — одна ответственность (bounded context) |
| **Своя БД** | Сервис владеет своими данными (database per service) |
| **Взаимодействие через API** | REST/gRPC/события (Kafka) |
| **Независимый жизненный цикл** | Можно обновлять сервис не трогая другие |

## Как разбивать на сервисы

По **бизнес-возможностям**, а не по техническим слоям:

```
НЕПРАВИЛЬНО (по слоям):
  UserInterface-Service, BusinessLogic-Service, DataAccess-Service

ПРАВИЛЬНО (по домену):
  UserService, OrderService, PaymentService, NotificationService
```

Правила декомпозиции:
1. **Границы по бизнес-функции** (что делает сервис)
2. **Независимость изменения** (два модуля часто меняются вместе → один сервис)
3. **Независимость масштабирования** (разная нагрузка → разные сервисы)
4. **Независимость команд** (каждая команда владеет своим сервисом)

## Плюсы микросервисов

✅ **Независимое развёртывание** — обновил один сервис без даунтайма остальных  
✅ **Изоляция сбоев** — упал Payments, но Orders работает  
✅ **Масштабирование по нагрузке** — копируем только нагруженный сервис  
✅ **Независимость технологии** — каждый сервис на своём стеке  
✅ **Скорость команд** — параллельная разработка, маленькие команды  
✅ **Чёткие границы** — понятная модель предметной области  

## Минусы микросервисов

❌ **Сложность распределённых систем** — сетевые сбои, задержки  
❌ **Распределённая трассировка** — сложно отлаживать  
❌ **Данные размазаны** — нет JOIN'ов между БД сервисов  
❌ **Операционная сложность** — мониторинг, логи, оркестрация (K8s)  
❌ **Сетевые накладные расходы** — каждый вызов через сеть  
❌ **Труднее тестировать** — интеграционные тесты сложнее  
❌ **Дублирование кода** — общие утилиты приходится шарить через библиотеки  

## Когда микросервисы оправданы

| Использовать микросервисы | Использовать монолит |
|---------------------------|----------------------|
| Большая команда (50+ человек) | Маленькая команда (до 10) |
| Разные домены с независимым развитием | Простое приложение/прототип/стартап |
| Высокие требования к масштабируемости | Невысокая нагрузка |
| Несколько команд хотят деплоить независимо | Быстрая итерация MVP |
| Уже выросший монолит, который мешает | Нет освоенного инструментария (K8s, CI/CD) |

> **Правило**: начинайте с монолита. Микросервисы — для роста, а не для старта. Хорошо разложенный монолит — первый шаг к микросервисам.

## Ключевые практики в микросервисах

### Service Discovery
Сервисы находят друг друга динамически (не по IP):
- **Consul, Eureka, Kubernetes DNS** — реестр сервисов

### API Gateway
Единая точка входа: маршрутизация, аутентификация, rate limiting.

### Circuit Breaker (предохранитель)
Защита от каскадных сбоев: если сервис падает — не пытаться каждая 10 мс, а «открыть предохранитель» (сразу отвечать fallback'ом).

```
# Пример: Circuit Breaker (псевдокод)
def call_payments():
    if breaker.state == "OPEN":        # уже поняли, что сервис лежит
        return fallback()              # не ходим в сеть, сразу запасной ответ
    try:
        result = payments_api.charge()
        breaker.record_success()       # закрываем постепенно
        return result
    except TimeoutError:
        breaker.record_failure()       # при падении порога → OPEN
        return fallback()
```

### Distributed Tracing
`trace_id` прокидывается через все сервисы, чтобы собрать весь путь запроса в один лог.

### Saga (распределённые транзакции)
Нет атомарной транзакции в микросервисах → компенсация.

### Database per Service
Каждый сервис владеет своей БД. Общий доступ к чужой БД — антипаттерн!

## Практическое задание

**Сценарий:** Вы проектируете систему для ресторана доставки еды. Есть следующие функции: каталог меню, оформление заказа, оплата, кухня, доставка, отзывы, лояльность (бонусы).

**Задание:**
1. Определите границы микросервисов (каждый сервис — ответственность,owns данные).
2. Какие сервисы могут использовать одну базу данных, а какие — нет? Обоснуйте.
3. Как вы организуете взаимодействие между «Заказ» и «Кухня» — синхронно или асинхронно? Почему?
4. Как вы решите проблему «доставки одного заказа, если курьер отказался» (сага /补偿)?

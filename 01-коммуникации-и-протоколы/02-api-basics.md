# API (Application Programming Interface)

> Контракт взаимодействия между системами. Набор правил, по которым одна программа обращается к другой.

## Что такое API

**API** — это интерфейс, который определяет, **как** и **с какими данными** можно обращаться к системе.

Аналогия: **меню в ресторане** — вы (клиент) выбираете блюдо из списка, не зная, как его готовят (внутренняя логика ресторана).

## Виды API

### По типу доступа

| Вид | Описание | Пример |
|-----|----------|--------|
| **Public** (открытый) | Доступен всем | Stripe API, Google Maps API |
| **Partner** (партнёрский) | Доступен по договорённости | API банков для интеграций |
| **Private** (внутренний) | Только внутри компании | API микросервисов |

### По протоколу

| Вид | Протокол | Когда применять |
|-----|----------|-----------------|
| **REST** | HTTP/JSON | Стандарт для веб-API, 90% случаев |
| **gRPC** | HTTP/2 + Protobuf | Внутренние сервисы, высоконагруженные системы |
| **GraphQL** | HTTP/GraphQL | Гибкая выборка данных, клиент определяет структуру |
| **SOAP** | XML/SOAP | Легаси-системы, банковская сфера (редко) |
| **WebSocket** | TCP (постоянное соединение) | Реалтайм-коммуникация |

## Жизненный цикл API

```
1. Проектирование ──► 2. Разработка ──► 3. Тестирование ──► 4. Документация
                                                                    │
5. Мониторинг ◄────── 4. Эксплуатация ◄─────────────────────────────┘
```

## Компоненты хорошего API

1. **Ресурсы** — что моделируется (users, orders, products)
2. **Методы** — операции над ресурсами (GET, POST, PUT...)
3. **Формат данных** — JSON/XML
4. **Авторизация** — как клиент доказывает право доступа
5. **Ошибки** — понятные коды и сообщения
6. **Документация** — описание всех endpoints (OpenAPI/Swagger)
7. **Версионирование** — /v1/, /v2/, заголовки

## Спецификации API

| Спецификация | Что это | Применение |
|--------------|---------|------------|
| **OpenAPI** (Swagger) | Описание REST API (YAML/JSON) | Документация + авто-генерация клиентов |
| **AsyncAPI** | Описание событийных API | Kafka, WebSocket, message queues |
| **GraphQL Schema** | Типы и операции GraphQL | GraphQL API |

Пример OpenAPI:

```yaml
openapi: 3.0.0
info:
  title: Orders API
  version: 1.0.0
paths:
  /orders:
    get:
      summary: Список заказов
      parameters:
        - name: status
          in: query
          schema:
            type: string
      responses:
        "200":
          description: OK
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: "#/components/schemas/Order"
```

## Версионирование API

Почему важно: **не ломать** существующих клиентов при изменениях.

| Способ | Пример | Плюсы/Минусы |
|--------|--------|--------------|
| В URL | `/api/v1/orders`, `/api/v2/orders` | Просто и понятно / URL раздувается |
| В заголовке | `Accept: application/vnd.api+json;version=2` | Чистый URL / сложнее для клиентов |
| Query param | `/api/orders?version=2` | Просто / не рекомендуется |

## Как аналитик участвует в создании API

1. **Собирает требования** и бизнес-сценарии
2. **Определяет ресурсы** и операции над ними
3. **Описывает контракт** — какие данные приходят/уходят
4. **Согласовывает** с командой разработки
5. **Описывает ошибки** и граничные случаи

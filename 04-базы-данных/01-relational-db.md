# Реляционные базы данных

> Данные хранятся в **таблицах** со связями между ними. Язык запросов — SQL.

## Что такое реляционная БД

**Реляционная БД (RDBMS)** — данные организованы в таблицы, связанные через ключи.

```
┌──────────────┐        ┌──────────────────┐
│   users      │        │    orders        │
├──────────────┤        ├──────────────────┤
│ id (PK)      │◄───────┤ id (PK)          │
│ name         │  FK    │ user_id (FK) ────┤
│ email        │        │ total            │
│ created_at   │        │ status           │
└──────────────┘        └──────────────────┘
```

Примеры: **PostgreSQL, MySQL, Oracle, SQL Server, SQLite**.

## Базовый SQL

### DDL — определение структуры (Data Definition Language)

```sql
-- Создать таблицу
CREATE TABLE users (
    id         BIGSERIAL PRIMARY KEY,
    name       VARCHAR(100) NOT NULL,
    email      VARCHAR(255) UNIQUE NOT NULL,
    created_at TIMESTAMP DEFAULT now()
);

-- Изменить таблицу (добавить колонку)
ALTER TABLE users ADD COLUMN phone VARCHAR(20);

-- Удалить таблицу
DROP TABLE users;
```

### DML — операции с данными (Data Manipulation Language)

```sql
-- INSERT - добавить
INSERT INTO users (name, email) VALUES ('Иван', 'ivan@example.com');

-- SELECT - выбрать
SELECT id, name, email FROM users WHERE email = 'ivan@example.com';

-- UPDATE - обновить
UPDATE users SET name = 'Иван Петров' WHERE id = 1;

-- DELETE - удалить
DELETE FROM users WHERE id = 1;
```

### SELECT с JOIN — связи между таблицами

```sql
SELECT u.name, o.total, o.status
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.id = 42;
```

| JOIN | Что вернёт |
|------|-----------|
| **INNER JOIN** | Только строки, где есть совпадение в обеих таблицах |
| **LEFT JOIN** | Все строки из левой таблицы + совпадения из правой |
| **RIGHT JOIN** | Все строки из правой + совпадения из левой |
| **FULL JOIN** | Все строки из обеих таблиц |

## Нормализация

**Нормализация** — процесс устранения избыточности и аномалий в данных путём разделения на таблицы по формам.

### Формы нормализации (правила)

| Форма | Правило | Пример нарушения |
|-------|---------|------------------|
| **1НФ** | Атомарность: каждое поле — одно значение | `phone: "+7 900, +7 911"` (список в одном поле) |
| **2НФ** | Нет частичной зависимости от составного ключа | При ключе (order_id, product_id) поле `customer_name` зависит только от order_id |
| **3НФ** | Нет транзитивной зависимости | `city → region`, нельзя чтобы регион лежал в таблице user |
| **BCNF** | Сильнее 3НФ (для составных ключей) | Редкие особые случаи |

### Нормализация на практике (1НФ → 2НФ → 3НФ)

**До (не нормализовано):**
```
| order_id | customer | phone        | products              |
|----------|----------|--------------|-----------------------|
| 1        | Иван     | 79000000000  | Бургер, Кола          | ← 1НФ нарушена (список)
| 2        | Мария    | 79111111111  | Пицца                 |
```

**1НФ — атомарные значения (раздробить список):**
```
| order_id | customer | phone        | product_id |
|----------|----------|--------------|------------|
| 1        | Иван     | 79000000000  | 101        |   ← Бургер
| 1        | Иван     | 79000000000  | 102        |   ← Кола
| 2        | Мария    | 79111111111  | 103        |   ← Пицца
```
Но: `customer`, `phone` повторяются для каждого товара заказа → избыточность.

**2НФ — убрать частичную зависимость (выделить заказы в отдельную таблицу):**
```
orders:  | order_id | customer_id | ...     |
items:   | order_id | product_id  | qty     |
```
Каждое поле таблицы зависит от полного ключа.

**3НФ — убрать транзитивные зависимости (телефон в users, а не в orders):**
```
users:    | user_id | name  | phone       |
orders:   | order_id| user_id | ...      |
items:    | order_id| product_id | qty   |
products: | product_id | name | price     |
```

### Зачем нормализовать

✅ Нет дублирования (данные в одном месте)  
✅ Нет аномалий обновления (обновил в одном месте — изменилось везде)  
✅ Нет аномалий вставки (нельзя создать заказ без пользователя)  
✅ Нет аномалий удаления (удалил товар → остались лишние данные)  
✅ Экономия места  

### Минусы избыточной нормализации

❌ Много JOIN'ов → медленные запросы  
❌ Сложные запросы для чтения  
❌ При больших объёмах данных и высокой нагрузке — неэффективно  

## Денормализация

**Денормализация** — намеренное **добавление избыточности** для ускорения чтения.

### Пример

**Нормализованная модель:**
```sql
-- Получить имя покупателя для заказа (2 JOIN'а)
SELECT u.name
FROM orders o
JOIN users u ON u.id = o.user_id
WHERE o.id = 77;
```

**Денормализованная модель** — добавили `customer_name` прямо в заказ:
```
| order_id | customer_name | total | status |
|----------|----------------|-------|--------|
| 77       | Иван           | 1500  | paid   |
```
Теперь: `SELECT customer_name FROM orders WHERE id = 77` — **без JOIN'ов!**

### Когда денормализовать

| Ситуация | Решение |
|----------|---------|
| Много чтения, мало записи (90% READ) | Денормализация оправдана |
| Частые и тяжёлые JOIN'ы | Дублировать часто нужные поля |
| Big Data / аналитика (OLAP) | Денормализация — норма |
| Синхронизация микросервисов | Кэш данных в сервисе |

### Риски денормализации

⚠️ **Избыточность** — данные в двух местах  
⚠️ **Аномалии обновления** — надо обновлять в обоих местах  
⚠️ **Сложность записи** — запись дороже  
⚠️ **Риск рассинхронизации** — если обновили в одном месте, но не в другом  

### Правило-шпаргалка

> **Нормализация — для целостности.**  
> **Денормализация — для скорости.**
>
> Начинай с нормализованной схемы, а денормализуй **точечно** по мере появления проблем производительности.

## OLTP vs OLAP

| | OLTP | OLAP |
|---|------|------|
| Расшифровка | Online Transaction Processing | Online Analytical Processing |
| Нагрузка | Много мелких операций Записи | Массовое чтение агрегатов |
| Пример | Кассовый аппарат, заказы | Отчёты, аналитика |
| Схема | Нормализованная | Денормализованная (звёзды) |
| БД | PostgreSQL, MySQL | ClickHouse, Redshift, Snowflake |

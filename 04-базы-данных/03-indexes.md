# Индексы в базах данных

> Структуры данных, ускоряющие поиск. При правильном использовании ускоряют в десятки раз, при неправильном — вредят.

## Что такое индекс

**Индекс** — отсортированная структура (обычно B-tree), которая позволяет БД находить строки **не перебирая всю таблицу**.

```
БЕЗ индекса:  БД сканирует ВСЕ строки (Full Table Scan)
┌─────────────────────────────┐
│ users: 1 млн строк          │
│ ищем email = 'ivan@x.com'   │
│ ── проверяем каждую строку  │  → 1 млн операций, ~50 мс
└─────────────────────────────┘

С ИНДЕКСОМ: БД идёт по дереву
┌─────────────────────────────┐
│ INDEX on users(email):      │
│        B-tree               │
│ищем 'ivan@x.com' бинарный   │  → ~20 операций, <1 мс
│поиск по дереву              │
└─────────────────────────────┘
```

Наглядно: искать имя в **телефонном справочнике** (отсортирован — индекс) vs **читать весь список по порядку**.

## Создание индекса

```sql
-- Обычный индекс
CREATE INDEX idx_users_email ON users(email);

-- Уникальный индекс (плюс гарантия уникальности)
CREATE UNIQUE INDEX idx_users_email ON users(email);

-- Составной индекс (на несколько колонок, порядок важен!)
CREATE INDEX idx_orders_user_status ON orders(user_id, status);

-- Частичный индекс (только для части строк)
CREATE INDEX idx_users_active ON users(email) WHERE is_active = true;

-- Удалить индекс
DROP INDEX idx_users_email;
```

## Когда индекс ускоряет

| Операция | SQL | Влияние индекса |
|----------|-----|-----------------|
| Поиск по равенству | `WHERE email = 'x'` | ✅ Огромное |
| Поиск по диапазону | `WHERE created_at BETWEEN a AND b` | ✅ Большое |
| Сортировка | `ORDER BY created_at` | ✅ Индекс уже отсортирован |
| JOIN | `JOIN ... ON o.user_id = u.id` | ✅ Индексы на ключах |
| Группировка | `GROUP BY status` | ✅ Частично |
| LIKE '%text%' | `WHERE name LIKE '%x%'` | ❌ Индекс не поможет (средняя маска) |

> ⚠️ **Общее правило**: индекс помогает, когда запрос выбирает **малую долю** строк (< 5-10%). Если запрос выбирает половину таблицы — БД всё равно пойдёт полным сканированием (эффективнее).

## Плюсы индексов

✅ Ускорение SELECT (в десятки–сотни раз)  
✅ Ускорение JOIN'ов  
✅ Ускорение сортировки и фильтрации  
✅ Уникальные индексы гарантируют уникальность данных  

## Минусы индексов

❌ **Занимают место** (дублируют данные колонок)  
❌ **Замедляют INSERT/UPDATE/DELETE** — при каждой записи индекс тоже обновляется  
❌ **Усложняют схему** — лишние индексы путают  
❌ **Планировщик может не использовать** нужный индекс (или выбрать неправильный)  

## Когда НЕ ставить индекс

- Таблица маленькая (< 1000 строк) — полное сканирование быстрее
- Колонка с малым разнообразием значений (пол, boolean) — индекс почти не помогает
- Часто обновляемая таблица с уже несколькими индексами — запись станет дороже
- Широкие колонки (большой текст) — индекс огромный

## Составные индексы и правило префикса

Индекс на `(user_id, status)` ускоряет:

```sql
WHERE user_id = 42                      ✅ использует первую колонку
WHERE user_id = 42 AND status = 'paid'  ✅ использует обе
WHERE status = 'paid'                   ❌ НЕ использует! (нет префикса user_id)
```

> **Правило**: составной индекс работает, если запрос фильтрует по **префиксу** колонок слева направо.

## EXPLAIN — как аналитик проверяет использование индексов

Все БД показывают план запроса:

```sql
-- PostgreSQL
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42;
```

```
Index Scan using idx_orders_user_status on orders  ← использует индекс!
  Index Cond: (user_id = 42)
  Execution Time: 0.05 ms
```

## Шпаргалка для аналитика

```
Куда смотреть, когда API тормозит?

1. Медленные запросы в БД?
   → проверить план запроса (EXPLAIN)
2. Есть ли индекс под условие WHERE?
   → нет → добавить
3. Запрос выбирает много строк?
   → индекс не спасёт, думать о другом (кэш, денормализация)
4. Столбец часто изменяется и индексов уже много?
   → не плодить, искать лишние
```

Практическое правило: **индексировать колонки** которые:
- часто в `WHERE` / `JOIN` / `ORDER BY`
- высокоселективны (много уникальных значений)

и **не индексировать** все подряд.

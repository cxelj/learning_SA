
## Практическое задание

**Сценарий:** Вы проектируете API для управления списком задач (To-Do). Задачи имеют: id, название, описание, статус (todo/in_progress/done), дедлайн.

**Задание:**
1. Определите, какой HTTP-метод подходит для каждого действия: создать задачу, изменить только статус, полностью заменить задачу, удалить, получить список задач с фильтрацией по статусу.
    - `POST для создания задачи`
    - `PATCH для изменения статуса`
    - `PUT для полной замены задачи`
    - `DELETE для удаления`
    - `GET для списка задач с фильтрацие по статусу`
2. Обоснуйте, почему для изменения статуса выбран PATCH, а не PUT (или наоборот).
    - `Для изменения статуса использован PATCH, т.к. не требуется изменение значений других заголовков.`
3. Составьте 2 curl-запроса: один для создания задачи, другой для частичного обновления.
    - 
    ```
    curl -X POST https://example.com/To-Do/tasks \
            -H "Content-type: application/json" \
            -H "Authorization: Bearer <TOKEN>" \
            -d '{
              "title": "Список покупок",
              "description": "Хлеб, Яйца, Молоко",
              "status": "in_progress",
              "priority": "high",
              "deadline": "2026-09-18"
            }'
    (id - генерируется на сервере, если на клиенте - то передается в теле запроса "id": "5649e-4s26t-43h5")
    ```
    ```
    curl -X PATCH https://example.com/To-Do/tasks/5649e-4s26t-43h5 \
            -H "Content-type: application/json" \
            -H "Authorization: Bearer <TOKEN>" \
            -d '{
              "priority": "done"
            }'
    ```

## Вопросы для самопроверки

1. Какой метод использовать для создания ресурса? Для полного обновления?
    - `POST для создания`
    - `PUT для полного обновления`
2. Какие методы идемпотентны и почему?
    - `GET, PUT, DELETE, HEAD, OPTIONS, т.к. при повторном выполнении состояние будет тем же. POST - не идемпотентен (без использования Idempotency key) и PATCH (не гарантирует идемпотентное поведение и зависит от инструкций по изменению переданных в запросе, например увеличить значение на 10 - не индепотентный и установить значение 10 - индепотентный).`
3. Чем 401 отличается от 403?
    - `401 Ошибка аутентификации (сервер не знает кто клиент)`
    - `403 Ошибка авторизации (сервер знает кто клиент, но доступ не разрешён)`
4. Когда использовать 201, а когда 200?
    - `201 при успешном создании ресурса`
    - `200 при общих успешных запросах, когда сервер вернул запрошенные данные`
5. Почему POST не идемпотентен?
    - `Т.к. при каждом повторном запросе состояние сервера меняется (создается новая сущность), при этом метод POST можно сделать индепотентным путем добавления заголовка с уникальным ключом (Idempotency key)`

# Аутентификация и авторизация

> Два разных процесса: **кто ты** (аутентификация) и **что тебе можно** (авторизация).

## Разница (важно!)

| | Аутентификация (Authentication) | Авторизация (Authorization) |
|---|--------------------------------|------------------------------|
| Вопрос | **Кто** ты? | **Что** тебе можно? |
| Проверка | Логин/пароль, токен | Права, роли, политики |
| Ответ | Успех → токен/сессия | Успех → доступ к ресурсу |
| По-простому | Пропуск в здание | Какие комнаты открыты |

```
Логин/пароль (аутентификация) → получил токен
Токен (авторизация) → доступен ли мне /admin?
```

## Способы аутентификации

### 1. Session-based (сессионная, cookie)

```
Клиент: POST /login (логин, пароль)
Сервер: создаёт сессию, сохраняет на сервере, отдаёт cookie (session_id)
Клиент: все запросы с cookie
Сервер: по session_id находит сессию в памяти/БД/Redis
```

| Плюсы | Минусы |
|-------|--------|
| Просто | Сервер хранит состояние |
| Легко отозвать | Масштабирование сложнее (shared session) |
| | Cookie уязвимы (CSRF) |

### 2. Token-based (JWT)

**JWT** (JSON Web Token) — самодостаточный токен, подписанный сервером.

```
Структура JWT:
███████ ███████████ ███████████████
header  payload     signature

header:  {"alg":"HS256","typ":"JWT"}
payload: {"sub":"user-42","role":"admin","exp":1700000000}
signature: подпись (секрет сервера)
```

```
Клиент: POST /login → получает JWT
Клиент: GET /api/orders
        Authorization: Bearer <JWT>
Сервер: проверяет подпись + срок → НЕ хранит сессию (stateless!)
```

| Плюсы | Минусы |
|-------|--------|
| Stateless (сервер не хранит сессию) | Отозвать сложно (до истечения) |
| Масштабируется легко | Пока нельзя уменьшить (без refresh) |
| Всё в одном токене | Размер (может быть большим) |
| Стандарт | Секрет на сервере критичен |

### 3. OAuth 2.0 (делегированный доступ)

Используется, когда **третье лицо** получает доступ от имени пользователя.

```
"Войти через Google": Google — Authorization Server
```

```
Пользователь → Наше приложение: "войти через Google"
Наше приложение → Google: "дай доступ"
Google → Пользователь: "согласен?"
Пользователь → Google: да
Google → Нашему приложению: code → token
Наше приложение: с token'ом ходит в API Google
```

| OAuth-элементы | Роль |
|----------------|------|
| Resource Owner | Пользователь (владелец данных) |
| Authorization Server | Сервер auth (Google, GitHub) |
| Client | Наше приложение |
| Scope | Какие права запрашиваются |

### 4. OpenID Connect (OIDC)
Надстройка над OAuth 2.0: добавляет **ID token** — кто пользователь. OIDC = аутентификация, OAuth = авторизация/делегирование.

### 5. API-ключи
Простой ключ для сервис-то-сервис.

```http
X-API-Key: k9f2js82js
```

| Плюсы | Минусы |
|-------|--------|
| Просто | Слабый (если ключ украли — всё, что с ним) |
| Для сервисных интеграций | Не привязан к пользователю |

## Сравнение способов

| Способ | Для чего | Stateless | Отзыв | Сложность |
|--------|----------|-----------|-------|-----------|
| Сессии (cookie) | Веб-приложения | ❌ | ✅ легко | Низкая |
| JWT | API, SPA, мобильные | ✅ | ❌ сложно | Средняя |
| OAuth 2.0 | «Войти через...» | ✅ | ✅ | Высокая |
| API-ключ | Сервис-сервис | ✅ | Средне | Низкая |

## Схема полного потока (JWT)

```
┌────────┐  ① POST /auth/login        ┌──────────┐
│ Клиент │ ──────────────────────────►│   API    │
│        │    {login, password}       │          │
│        │                            │ ② проверка
│        │ ◄───────────────────────── │     пароля
│        │  {access_token, refresh_token}
│        │                            │
│        │  ③ GET /api/orders         │ ④ проверка
│        │ ──────────────────────────►│   JWT    │
│        │     Authorization: Bearer  │   (валidный?) │
│        │ ◄───────────────────────── │          │
│        │  200 + данные              │          │
└────────┘                            └──────────┘
```

## Refresh-токены

Access-токен живёт недолго (15 мин–1 час). Refresh-токен — дольше (недели), позволяет получить новый access без логина.

```
Access-токен истёк → клиент шлёт refresh-токен → получает новый access.
Access-токены хранятся в памяти/секрете; refresh — в БД (отзыв возможен).
```

## Права и роли (RBAC)

**RBAC** (Role-Based Access Control) — права через роли.

```
Role: admin  → может всё
Role: manager → create, read, update
Role: user   → read only for own data
```

```python
ROLES = {
    "admin":   {"read", "write", "delete", "manage_users"},
    "manager": {"read", "write"},
    "user":    {"read"},
}
```

Проверка на сервере:
```python
def delete_order(user, order):
    if "delete" not in ROLES[user.role]:
        return 403  # Forbidden
    ...
```

## Этапы авторизации

```
1. АУТЕНТИФИКАЦИЯ — кто ты?
   login/password, токен → идентификация
2. АВТОРИЗАЦИЯ — что тебе можно?
   роль/права → доступ к ресурсу (RBAC, ABAC, ACL)
3. АУДИТ — что ты делал?
   логирование действий (кто, когда, что изменил)
```

## Распространённые ошибки (OWASP)

| Ошибка | Проблема |
|--------|----------|
| Положить JWT в URL | Попадёт в логи/историю браузера |
| Не проверять срок | Истёкшие токены работают |
| Слабый secret | Подпись можно подделать |
| Вернуть токен клиенту в открытом виде (без HTTPS) | Перехват |
| Проверять роль только на фронте | Достаточно поработать с API напрямую |
| IDOR (чужие ресурсы по id) | user_id из JWT, а не из запроса! |

# Кэширование API

> Хранение копий ответов, чтобы **не повторять** дорогие вычисления и обращения к БД.

## Зачем кэшировать

```
БЕЗ кэша:                             С КЭШЕМ:
Клиент → API → БД (каждый раз,        Клиент → API → [кэш!] → ответ
                    50 мс)                            (2 мс)
Сто повторных запросов = 100 обращений Сто повторных = 1 в БД + 99 из кэша
```

**Выигрыш:** латентность ↓, нагрузка на БД ↓, стоимость ↓.

## Уровни кэширования

| Уровень | Что кэшируется | Где живёт |
|---------|----------------|-----------|
| **Browser cache** | HTML, CSS, картинки | Браузер клиента |
| **CDN** | Статика, редко меняющиеся ответы | Глобальная сеть серверов |
| **API cache** | Ответы API (объекты) | Redis, in-memory |
| **Database cache** | Результаты запросов | query cache, materialized views |
| **Client app cache** | Данные приложения | Локально в приложении |

## Стратегии кэширования

### 1. Cache-Aside (ленивое кэширование) — самая популярная

Приложение само управляет кэшем.

```
Чтение:
  1. Смотрим в кэш (Redis)
  2. Есть? → вернуть из кэша
  3. Нет?  → читаем БД, кладём в кэш, отдаём

Запись:
  4. Пишем в БД
  5. Инвалидируем кэш (delete) или обновляем
```

```
Чтение:  Приложение → Кэш?  → есть → ответ
                          → нет → БД → записать в кэш → ответ

Запись:  Приложение → БД (записать) → инвалидировать кэш
```

### 2. Cache-Through (пишущий кэш)

Кэш — единственная точка доступа; он сам обновляет БД.

```
Запись: Приложение → Кэш (тот пишет в БД)
Чтение: Приложение → Кэш (тот при промахе читает БД)
```

Проще, но кэш становится источником данных.

### 3. Write-Behind (отложенная запись)

```
Приложение → Кэш (данные)  ← мгновенно
Кэш → БД (batch-запись позже, асинхронно)
```

Используется редко (риск потери при сбое кэша).

## HTTP-кэширование (для REST)

| Механизм | Как работает |
|----------|--------------|
| **Cache-Control** | Заголовок: `Cache-Control: max-age=3600` (1 час) |
| **ETag** | Хеш версии; клиент шлёт `If-None-Match` → `304 Not Modified` |
| **Last-Modified** | Дата; клиент шлёт `If-Modified-Since` |

Пример ETag:

```http
Ответ:  HTTP/1.1 200 OK
        ETag: "abc123def"

Повтор: GET /api/products/42
        If-None-Match: "abc123def"

Ответ:  HTTP/1.1 304 Not Modified   ← данные не отправляем, браузер берёт из кэша
```

## TTL (Time To Live)

| TTL | Когда |
|-----|-------|
| 60 сек | Быстро меняющиеся данные (цены, курсы) |
| 5 мин | Курсы валют, рейтинги |
| 1 час–сутки | Каталоги, статика, справочники |
| Долго | Неизменяемые данные (справочники) |

## Проблема устаревания (stale data)

```
Кэш хранит старую версию → пользователь видит устаревшие данные
```

**Инвалидация** — как освежить кэш:

| Метод | Описание |
|-------|----------|
| TTL | Просто: истекает время → запрос в БД |
| Event-based | При обновлении БД → delete из кэша (via Kafka-событие) |
| Versioning | Кэш с версией: `orders:v2:42` |

## Кэширование в микросервисах

```
Сервис A ──► Redis (кэш) ◄── БД
   │
   └── публикует событие "order.updated"
       → микросервисы-подписчики инвалидируют свои кэши
```

## Что кэшировать — правила

| Кэшировать | НЕ кэшировать |
|-----------|---------------|
| Редко меняющиеся данные (каталог) | Персональные данные целиком |
| Агрегированные отчёты | Динамические данные (баланс) |
| Авторизованные GET (с осторожностью) | Операции с побочными эффектами (POST) |
| Тяжёлые вычисления (аналитика) | Всё, что часто инвалидируется |

> ⚠️ Осторожно с кэшированием **персональных данных** — кэш должен учитывать пользователя
> (ключ вида `user:42:profile`).

## Кэш vs Идемпотентность vs Свежесть

| Концепция | Цель | Конфликт |
|-----------|------|----------|
| Кэш | Скорость | Может отдавать устаревшие данные |
| Идемпотентность | Безопасность повторов | Хранит результаты |
| Свежесть | Корректность | Требует инвалидации кэша |

Баланс: свежесть vs производительность. Для финансов — свежесть важнее.

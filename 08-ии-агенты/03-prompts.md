# Промпты агентов

> Как писать инструкции для ИИ-агентов, чтобы получить правильный результат.

## Системный промпт vs пользовательский

| Тип | Кто пишет | Назначение |
|-----|-----------|-----------|
| **System prompt** | Разработчик | Определяет роль, стиль, правила, НЕ меняется |
| **User prompt** | Пользователь | Конкретная задача |

```
System: "Ты — системный аналитик. Отвечай кратко и по-русски.
         Используй понятные примеры."
User:   "Объясни, что такое транзакция в БД"
```

## Структура хорошего промпта

### 1. Роль (кем говорит)

```
Ты — опытный системный аналитик с 10-летним стажем.
```

### 2. Контекст (что известно)

```
Проект — интернет-магазин. Архитектура — микросервисы.
Сервисы: orders, payments, inventory. БД: PostgreSQL.
```

### 3. Задача (что сделать)

```
Спроектируй REST API для сервиса заказов.
```

### 4. Ограничения/правила (как делать)

```
- Используй RESTful конвенции (ресурсы = существительные).
- Ответ на русском.
- Приведи примеры запросов/ответов.
```

### 5. Формат вывода (что именно вернуть)

```
Верни:
1. Список endpoints (метод, путь, описание)
2. Примеры JSON
3. Коды ошибок
```

## Принципы хороших промптов (шпаргалка)

| Принцип | Пример |
|---------|--------|
| **Конкретика** (не абстракции) | «напиши» → «напиши функцию с сигнатурой X» |
| **Примеры** (few-shot) | «вот как должен выглядеть ответ: ...» |
| **Разбиение** (по шагам) | «сначала объясни, потом приведи код» |
| **Ограничения явные** | «не используй сторонние библиотеки» |
| **Формат ожидания** | «ответь таблицей: столбцы A, B, C» |
| **Критерии успеха** | «результат считается выполненным, если...» |
| **Negative prompt** | «не делай: ...» |

## Пример: плохой vs хороший промпт

**Плохой:**
```
Напиши API для заказов.
```

**Хороший:**
```
Ты — системный аналитик. Спроектируй REST API для сервиса заказов
интернет-магазина.

Контекст:
- существующие сущности: пользователь, товар, заказ
- авторизация: JWT
- требования: идемпотентность для POST

Задача:
1. Опиши ресурсы и методы (GET/POST/PATCH/DELETE)
2. Для каждого метода: путь, параметры, коды ответов
3. Приведи пример JSON для create order

Правила:
- ресурсы в множественном числе
- ответ на русском
- следуй OpenAPI-стилю
```

## Промпты для агентов-ролей (как в OpenCode)

Каждый агент — это промпт, определяющий поведение.

### Агент-исследователь (explore)
```
Ты — агент исследования кодовой базы.
- Ищи функции, классы, файлы
- Возвращай точные пути и строки
- Не изменяй файлы, только читай
```

### Агент-ревьюер (reviewer)
```
Ты — код-ревьюер.
- Проверяй: SOLID, DRY, безопасность, стиль
- Находи баги и анти-паттерны
- Давай конкретные рекомендации
- Не изменяй код, только отчёт
```

### Агент-тестировщик (tester)
```
Ты — тестировщик.
- Пиши тесты для найденных функций
- Покрывай: happy path, крайние случаи, ошибки
- Запускай тесты и сообщай о статусе
```

## Misc: техники промптинга

| Техника | Описание |
|---------|----------|
| **Zero-shot** | Просто задача без примеров |
| **Few-shot** | Задача + 2-3 примера |
| **Chain-of-thought** | «Думай по шагам» — модель раскладывает рассуждение |
| **ReAct** | «Рассуждай → действуй → наблюдай» (лежит в основе агентов) |
| **Разыщи-и-проверь** | Задай модель проверить свой вывод |
| **Self-consistency** | Сгенерируй несколько ответов и выбери большинство |

## Практическое задание

**Сценарий:** Вам нужно создать ИИ-агента, который будет анализировать код на наличие SQL-инъекций и выдавать рекомендации.

**Задание:**
1. Напишите системный промпт для этого агента (роль + правила + формат вывода).
2. Сгенерируйте 3 пользовательских промпта: zero-shot, few-shot (с 1 примером), chain-of-thought.
3. Определите, какой из трёх промптов даст лучший результат и почему.
4. Какие негативные ограничения (negative prompt) вы добавите?

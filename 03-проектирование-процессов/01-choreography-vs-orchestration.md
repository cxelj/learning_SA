# Хореография vs Оркестрация

> Два подхода к организации взаимодействия сервисов в распределённой системе.

## Аналогия из жизни

Представьте **оркестр**:

- **Оркестрация** — есть **дирижёр**. Все музыканты смотрят на него и играют по его команде. Дирижёр знает всю партитуру.
- **Хореография** — танцоры **сами** знают свои движения и реагируют на движения партнёров. Нет главного — есть согласованность.

## Оркестрация (Orchestration)

**Центральный компонент** (оркестратор) вызывает сервисы по очереди и управляет процессом.

```
                    ┌─────────────────────┐
                    │   ORCHESTRATOR      │ ← знает ВЕСЬ процесс
                    │   (OrderService)    │
                    └─────────┬───────────┘
              ┌───────────────┼───────────────┐
              │               │               │
         ┌────▼────┐     ┌────▼────┐     ┌────▼────┐
         │ Payment │     │ Inventory│    │ Shipping │
         │ (контроль│    │ (контроль │    │ (контроль) │
         │ платёжа) │     │ складом) │    │ доставкой)│
         └─────────┘     └─────────┘    └──────────┘
```

**Как это работает:**
```
Оркестратор: ① создать заказ
             ② Вызвать PaymentService → запросить платёж
             ③ Вызвать InventoryService → зарезервировать товар
             ④ Вызвать ShippingService → сформировать отгрузку
             ⑤ статус заказа = "confirmed"
```

Оркестратор знает **все шаги и их порядок**. Сервисы — «тупые» исполнители.

## Хореография (Choreography)

**Нет центрального управляющего.** Каждый сервис сам реагирует на события и публикует свои.

```
 Событие: OrderCreated ──► все слушают
        │
        ├──► PaymentService: "услышал OrderCreated"
        │       │  делает платёж
        │       └──► публикует PaymentCompleted
        │
        ├──► InventoryService: "услышал OrderCreated"
        │       │  резервирует товар
        │       └──► публикует InventoryReserved
        │
        └──► ShippingService: "услышал PaymentCompleted + InventoryReserved"
                │  создаёт отгрузку
                └──► публикует OrderShipped
```

Каждый сервис **сам решает**, что делать при событии. Связь через **транспорт событий** (Kafka, очередь).

## Сравнительная таблица

| Критерий | Оркестрация | Хореография |
|----------|-------------|-------------|
| Управление | Центральное (один компонент) | Децентрализованное (каждый сам) |
| Кто знает процесс | Оркестратор | Никто целиком (каждый свою часть) |
| Связность сервисов | Низкая (только с оркестратором) | Высокая (все со всеми через события) |
| Сложность мониторинга | Проще (видно кто где) | Сложнее (процесс «размазан») |
| Отладка/трассировка | Проще | Сложнее |
| Отказоустойчивость | Оркестратор — single point of failure | Нет единой точки отказа |
| Масштабирование | Оркестратор — узкое место | Легче масштабировать |
| Скорость изменений | Меняем оркестратор = меняем процесс | Легко добавлять новые сервисы-подписчики |
| Требуемая зрелость команды | Ниже | Выше |

## Правила выбора

```
Короткий и предсказуемый процесс (2-5 шагов)?
   └──► Оркестрация проще и понятнее

Процесс длинный, сложный, много ветвлений?
   └──► Оркестрация (нужен обзор) ИЛИ хореография (события)

Нужно легко подключать новые сервисы-реакции?
   └──► Хореография (новый подписчик = новое поведение)

Нет инструментов мониторинга процессов?
   └──► Оркестрация (легче отследить)

Высокая нагрузка, нужна отказоустойчивость?
   └──► Хореография (нет единой точки отказа)
```

## Паттерн Saga

**Saga** — способ управления распределённой транзакцией в микросервисах. Два способа реализации — прямо соответствуют нашим двум подходам:

| | Saga (оркестрация) | Saga (хореография) |
|---|--------------------|--------------------|
| Управление | Машина состояний / оркестратор | Через события |
| Шаги | Оркестратор вызывает по очереди | Сервисы реагируют на события |
| Компенсация | Оркестратор вызывает компенсирующие шаги | Каждый сервис публикует компенсацию |
| Пример структуры | SagaManager: `step1 → step2 → step3` или откат | PaymentCompleted → InventoryReserved → ... или PaymentFailed |

В примере с заказом:

```
ОРКЕСТРАЦИЯ (Saga-оркестратор):
  OrderSaga оркестратор:
    1. PaymentService.charge()
        ✗ не удалось → cancel(), компенсировать
        ✓ удалось
    2. InventoryService.reserve()
        ✗ не удалось → payment.refund() (компенсация)
        ✓ удалось
    3. ShippingService.ship()
        ...
```

```
ХОРЕОГРАФИЯ (Saga-события):
  OrderCreated → PaymentService слушает
  PaymentCompleted → InventoryService слушает
  InventoryReserved → ShippingService слушает
  PaymentFailed → OrderService (компенсация, отмена заказа)
```

# Polling vs Pushing

> Два подхода получения обновлений от сервера. Ключевой вопрос: **кто инициатор** — клиент или сервер?

## Суть различий

```
POLLING (опрос):
  Клиент ──► GET /api/updates ──► Сервер     ← клиент спрашивает
  Клиент ◄── нет новых/данные ── Сервер
  (повторяется каждые N секунд)

PUSHING (подталкивание):
  Сервер ──► данные ──► Клиент               ← сервер сам отправляет
```

| Вопрос | Polling | Pushing |
|--------|---------|---------|
| Кто инициатор | Клиент (спрашивает) | Сервер (отправляет) |
| Соединение | Открывается каждый раз | Постоянное (WebSocket) или подписка (Kafka) |
| Задержка | До N секунд (период опроса) | Минимальная |
| Нагрузка на сервер | Выше (пустые запросы) | Ниже (нет лишних запросов) |
| Простота | Проще | Сложнее |
| Реалтайм | Нет | Да |

## Виды polling

### 1. Обычный polling
Клиент опрашивает через фиксированный интервал.

```
каждые 10 секунд:
  GET /api/order-status?id=42
  → { "status": "processing" }
  GET /api/order-status?id=42
  → { "status": "processing" }
  ...
  → { "status": "done" }   ← когда-нибудь ответит
```

✅ Просто реализовать  
❌ Много бесполезных запросов, задержка до N сек

### 2. Long polling (длинный опрос)
Клиент открывает запрос, сервер **держит соединение** пока нет данных, и отвечает моментально, когда они появляются.

```
GET /api/updates → (сервер молчит 20 сек, 30 сек...) → данные!
GET /api/updates → новые данные!
```

✅ Меньше пустых ответов  
❌ Сложнее, может разрываться по таймауту

### 3. SSE (Server-Sent Events)
HTTP-стрим: клиент подписывается, сервер шлёт события по одному соединению. Это **полу-push**.

```
GET /api/events (постоянное соединение)
← event: update, data: {...}
← event: update, data: {...}
```

✅ Push в одну сторону, простой, переиспользует HTTP  
❌ Однонаправленный, не работает на всех прокси по умолчанию

## Способы «пуша»

| Спосоob | Технология | Описание |
|---------|-----------|----------|
| WebSocket | TCP + Upgrade | Постоянное двустороннее соединение |
| SSE | HTTP | Сервер шлёт события по HTTP-стриму |
| Webhook | HTTP (POST на наш URL) | Сервер сам вызывает наш endpoint |
| Kafka/очередь | Транспорт событий | Посредник рассылает события подписчикам |
| Push-уведомления | FCM/APNs (мобайл) | ОС приложения получает уведомление |

## Критерии выбора

```
Как часто меняются данные?
│
├── Редко (раз в минуту +)  ──► POLLING (простой, нечастый опрос)
│
├── Часто, но допустима задержка (5-30 сек) ──► Long polling
│
├── Часто, нужен реалтайм (секунды) ──► WebSocket / SSE
│
└── Сервер инициирует (внешние события) ──► Webhook / Kafka
```

| Сценарий | Решение | Почему |
|----------|---------|--------|
| Статус заказа в мобильном приложении | **Polling** (long) | Обновление редкое, не нужно постоянное соединение |
| Онлайн-чат | **WebSocket** (push) | Реалтайм, двусторонний обмен |
| Платёжный шлюз уведомляет о платеже | **Webhook** (push) | Событие приходит извне, мы лишь принимаем |
| Мониторинг дашборда (раз в 30 сек) | **Polling** | Периодичность достаточна |
| Котировки биржи | **WebSocket** (push) | Миллисекунды решают |
| Уведомления для мобильного приложения | **Push (FCM)** | ОС сама будит приложение |

## Правило из поговорки

> «Если вы думаете, что данные изменились — спросите (polling).  
> Если вы точно знаете, что они изменились — отправьте (pushing).»

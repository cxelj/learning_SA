# Идемпотентность в API

> Гарантия, что повторный запрос даст ТОТ ЖЕ результат, что и первый. Критично для платёжей, заказов и уведомлений.

## Что такое идемпотентность

**Идемпотентность** — свойство операции: повторное выполнение не меняет результат относительно первого выполнения.

```
Идемпотентно:  DELETE /orders/42  → удалить
               DELETE /orders/42  → уже удалён (404), но итог тот же: заказ удалён ✅

НЕ идемпотентно: POST /orders  → создаёт заказ #1
                  POST /orders  → создаёт заказ #2 (дубль!) ❌
```

## Зачем это нужно

Сети ненадёжны. Клиент может **не получить ответ** и повторить запрос:

```
Клиент: POST /payments  (перевод 500 ₽)
  ... ответ потерялся, таймаут ...
Клиент: POST /payments  (снова!)  ← если не идемпотентно → ВТОРОЙ перевод!
```

Без идемпотентности: **деньги списаны дважды**. С идемпотентностью: повтор вернёт результат первого.

## Идемпотентные методы HTTP

| Метод | Идемпотентен | Почему |
|-------|--------------|--------|
| GET | ✅ | Только чтение |
| PUT | ✅ | Полная замена — повтор ставит то же значение |
| DELETE | ✅ | Повторное удаление несуществующего — тот же итог |
| HEAD | ✅ | Как GET, без тела |
| PATCH | ⚠️ | Зависит от реализации (обычно нет) |
| POST | ❌ | Создаёт новый ресурс каждый раз |

## Idempotency-Key (ключ идемпотентности)

**Решение для POST**: клиент генерирует уникальный ключ и передаёт его в заголовке.

```
Клиент                                    Сервер
  │   POST /payments                     │
  │   Idempotency-Key: order-123-abc     │
  │ ────────────────────────────────────►│  ключ = order-123-abc
  │                                      │  1-й раз: выполняем, сохраняем результат(ключ)
  │   [ответ потерялся]                  │
  │                                      │
  │   POST /payments                     │
  │   Idempotency-Key: order-123-abc     │  ← тот же ключ
  │ ────────────────────────────────────►│  2-й раз: возвращаем СОХРАНЁННЫЙ результат
  │   ← 200 (первый результат)           │  (НОВЫЙ платёж НЕ создаём)
```

## Правила Idempotency-Key

1. **Ключ генерирует клиент** (UUID) — на каждую «значимую» операцию
2. **Ключ уникален для операции**: order-123-abc — не переиспользуется
3. **Хранится** на сервере вместе с результатом (обычно в БД/Redis)
4. **Срок жизни** — как долго хранить ключи (часто 24ч — 7 дней)
5. **Одинаковый ключ + разные тела** → ошибка 422 (конфликт)

## Реализация (пример на псевдокоде)

```python
IDEMPOTENCY_TTL = 24 * 3600  # храним ключ сутки

def create_payment(request):
    key = request.headers["Idempotency-Key"]

    # 1. Проверяем: этот ключ уже обработан?
    exists = cache.get(f"idem:{key}")
    if exists:
        return Response(exists, status=exists.status)  # вернуть сохранённый результат

    # 2. Выполняем операцию
    payment = payment_service.charge(request.body)

    # 3. Сохраняем ключ → результат
    cache.set(f"idem:{key}", payment.to_dict(), ttl=IDEMPOTENCY_TTL)

    return Response(payment, status=201)
```

## Идемпотентность в разных контекстах

| Контекст | Идемпотентное действие |
|----------|------------------------|
| Платёж | Один платёж на один Idempotency-Key |
| Заказ | Повтор POST с тем же ключом → тот же заказ |
| Уведомление (email) | Не слать повторное письмо |
| Webhook retry | Обработчик возвращает тот же результат |
| Kafka (consumers) | At-least-once → обработчик не должен создавать дубли |

## Идемпотентность + Kafka (важно)

Kafka даёт **at-least-once** доставку → сообщения могут прийти **повторно**.

```
Producer отправил "user_registered"
  → сетевой сбой после обработки, но до offset commit
  → Consumer получает то же сообщение СНОВА

Если consumer просто создаст пользователя → дубль аккаунта!
```

**Решение:** обработка событий должна быть **идемпотентной**:
- Вставка `INSERT ... ON CONFLICT DO NOTHING` (или в уникальный ключ)
- Хранение `processed_event_ids` / `dedup` по `message_id`

```sql
-- Идемпотентная вставка (PostgreSQL)
INSERT INTO users (id, name, source_event_id)
VALUES (42, 'Иван', 'evt-123')
ON CONFLICT (source_event_id) DO NOTHING;
```

## Идемпотентные операции в БД

```sql
-- UPDATE — идемпотентен по своей природе
UPDATE accounts SET balance = balance + 100 WHERE id = 1;  -- НЕ идемпотентен (дважды = +200!)
UPDATE accounts SET balance = 500 WHERE id = 1;            -- идемпотентен (повтор = 500)
```

> При операциях «увеличить на N» нужна защита от повторов (ключ, dedup-таблица).

# Транзакции в базах данных

> Набор операций, выполняющихся **атомарно**: либо все выполняются, либо ни одна.

## Что такое транзакция

**Транзакция** — группа SQL-операций, которые выполняются как **одно целое**. Если любая операция не удалась — вся транзакция откатывается (rollback).

## Пример без транзакции

Перевод денег: списать с одного счёта, зачислить на другой.

```sql
-- Шаг 1: списать
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
-- 💥 ОШИБКА на шаге 2 (база упала, сеть отвалилась)

-- Шаг 2 НЕ выполнился → деньги списались, но не зачислились!
```

**Результат:** пользователь потерял 500 ₽. Катастрофа.

## Пример с транзакцией

```sql
BEGIN;  -- начали транзакцию

UPDATE accounts SET balance = balance - 500 WHERE id = 1;
UPDATE accounts SET balance = balance + 500 WHERE id = 2;

COMMIT; -- зафиксировали: оба изменения применились
```

Если бы ошибка случилась:

```sql
BEGIN;
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
-- ошибка...
ROLLBACK;  -- откат: первое изменение НЕ применится
```

**Деньги сохранились.** Оба UPDATE либо вместе применятся, либо оба откатятся.

## ACID — свойства транзакции

| Свойство | Что значит | Пример |
|----------|-----------|--------|
| **A**tomicity (Атомарность) | Все операции — одно целое: или все, или ничего | Перевод 500 ₽ списан и зачислен, или ничего |
| **C**onsistency (Согласованность) | После транзакции БД в корректном состоянии | Сумма всех балансов не изменилась |
| **I**solation (Изоляция) | Параллельные транзакции не мешают друг другу | Два перевода одновременно корректны |
| **D**urability (Долговечность) | После COMMIT'а данные переживут сбой | Зафиксировали — данные не пропадут при рестарте |

## BEGIN / COMMIT / ROLLBACK

```sql
BEGIN;
-- ... операции ...
COMMIT;    -- успешно зафиксировать

BEGIN;
-- ... операции ...
ROLLBACK;  -- отменить всё
```

Также можно управлять **точками сохранения**:

```sql
BEGIN;
SAVEPOINT sp1;              -- точка 1
UPDATE ...;
-- что-то пошло не так
ROLLBACK TO sp1;            -- откат только к точке 1, а не всей транзакции
UPDATE ...;                 -- идём дальше
COMMIT;
```

## Уровни изоляции (Isolation Levels)

Параллельные транзакции могут мешать друг другу. Уровни изоляции определяют, как сильно.

### Проблемы параллельности

| Проблема | Описание | Пример |
|----------|----------|--------|
| **Dirty Read** (грязное чтение) | Транзакция видит **незакоммиченные** данные другой | A изменяет счёт, B читает новое значение до COMMIT, A откатывается — B видел фантом |
| **Non-repeatable read** (неповторяющееся чтение) | За один запрос в той же транзакции данные **изменились** между чтениями | A читает баланс=100, B переводит деньги, A снова читает → баланс=50, в той же транзакции |
| **Phantom read** (фантомное чтение) | При повторном SELECT появились **новые строки** | A считает заказы=10, B добавляет заказ, A снова считает → 11 |

### Уровни изоляции (ANSI)

| Уровень | Dirty Read | Non-repeatable | Phantom | Применение |
|---------|-----------|----------------|---------|-----------|
| **READ UNCOMMITTED** | ❌ может быть | ❌ | ❌ | Почти никогда |
| **READ COMMITTED** (PostgreSQL по умолчанию) | ✅ нет | ❌ может | ❌ | Стандарт для веб-приложений |
| **REPEATABLE READ** (MySQL по умолчанию) | ✅ нет | ✅ нет | ❌ может | Средняя |
| **SERIALIZABLE** | ✅ нет | ✅ нет | ✅ нет | Самый строгий, но медленный |

```
Чем выше уровень изоляции → тем безопаснее, но медленнее (больше блокировок).
```

## Плюсы транзакций

✅ **Атомарность** — нет «половины операции» (деньги списались, но не зачислились)  
✅ **Согласованность** — данные всегда в корректном состоянии  
✅ **Изоляция** — параллельные операции корректны  
✅ **Долговечность** — зафиксированные данные не потеряются  
✅ **Восстановление после сбоев** — rollback автоматический  

## Минусы и ограничения транзакций

❌ **Производительность** — блокировки (locks) снижают параллельность  
❌ **Дедлоки (deadlock)** — две транзакции ждут друг друга  
❌ **Долгие транзакции** — держат блокировки, тормозят других  
❌ **Не работают между сервисами** — распределённая транзакция сложна (2-phase commit, Saga)  
❌ **Оверкилл** — не нужны для простых одиночных записей  

## Дедлок (Deadlock) — пример

```
Транзакция A: UPDATE accounts SET balance=... WHERE id=1;  ← взяла блокировку на id=1
Транзакция B: UPDATE accounts SET balance=... WHERE id=2;  ← взяла блокировку на id=2
Транзакция A: UPDATE accounts SET balance=... WHERE id=2;  ← ждёт блокировку на id=2 (у B)
Транзакция B: UPDATE accounts SET balance=... WHERE id=1;  ← ждёт блокировку на id=1 (у A)
```

**Результат:** взаимный блок. БД выявляет дедлок и откатывает одну транзакцию (выбросит ошибку).

**Профилактика:** брать блокировки всегда в одном порядке (например, сначала меньший id).

## Транзакции в микросервисах (распределённые)

В монолите одна БД = одна транзакция. В микросервисах каждый сервис — свою БД. **Классическая транзакция между сервисами невозможна.**

Решение — **Saga** (описано в модуле 3): компенсирующие шаги.

```
Распределённый перевод (2 сервиса):
  1. Сервис A списывает деньги (своя БД, транзакция A ✅)
  2. Сервис B зачисляет (своя БД, транзакция B ✅)
  НО: если B упал → A уже списал. Нужна компенсация:
  2'. Компенсирующее действие: A возвращает деньги.
```

## Когда включать транзакции

| Сценарий | Транзакция нужна |
|----------|------------------|
| Перевод средств между счетами | ✅ Да |
| Создание заказа + списание + обновление склада | ✅ Да |
| Вставка одной строки лога | ❌ Нет (одиночная запись) |
| Пакетное чтение данных | ❌ Нет (нет изменений) |
| Обновление статистики каждые 5 минут | ⚠️ да, но короткая |

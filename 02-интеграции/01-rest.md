# REST

> **Representational State Transfer** — архитектурный стиль для построения API на основе HTTP.

## Что такое REST

REST описывает, **как** система предоставляет доступ к своим ресурсам через HTTP. Это не протокол и не стандарт, а **набор принципов**.

## Принципы REST

### 1. Ресурсы и URI
Всё — ресурс. Каждый ресурс имеет адрес (URI).
```
GET /api/users/42        → пользователь с id=42
GET /api/users/42/orders → заказы пользователя 42
```

### 2. HTTP-методы как действия
```
GET    → прочитать
POST   → создать
PUT    → полностью обновить
PATCH  → частично обновить
DELETE → удалить
```

### 3. Stateless (без состояния)
Каждый запрос **самодостаточен**: содержит ВСЁ необходимое (токены, контекст). Сервер не хранит состояние сессии между запросами.

### 4. Представление данных (JSON/XML)
Клиент и сервер обмениваются данными в согласованном формате.

### 5. Коды состояния
200, 201, 400, 401, 404, 500... — семантика результата.

## Пример REST API (интернет-магазин)

```
GET    /api/v1/products              → список товаров
GET    /api/v1/products?category=food&page=2&limit=20
                                     → фильтр + пагинация
GET    /api/v1/products/42           → товар 42
POST   /api/v1/orders                → создать заказ
GET    /api/v1/orders/77             → получить заказ 77
PATCH  /api/v1/orders/77/status      → изменить статус
DELETE /api/v1/orders/77             → удалить заказ
```

## Пример запроса с curl

```bash
# Получить список продуктов (с токеном)
curl -X GET "https://api.example.com/v1/products" \
  -H "Authorization: Bearer eyJhbGciOi..." \
  -H "Accept: application/json"
```

```bash
# Создать заказ
curl -X POST "https://api.example.com/v1/orders" \
  -H "Authorization: Bearer eyJhbGciOi..." \
  -H "Content-Type: application/json" \
  -d '{
        "product_id": 42,
        "quantity": 2,
        "payment_method": "card"
      }'
```

## REST и CRUD

| Действие | HTTP метод | URL |
|----------|-----------|-----|
| **C**reate | POST | `/orders` |
| **R**ead | GET | `/orders/{id}` |
| **U**pdate | PUT/PATCH | `/orders/{id}` |
| **D**elete | DELETE | `/orders/{id}` |

## Чем REST хорош

✅ Простота и универсальность — работает везде  
✅ Кэширование на уровне HTTP  
✅ Масштабирование за счёт stateless  
✅ Легко документировать (OpenAPI)  
✅ Понятен разработчикам любого стека  

## Ограничения REST

❌ Избыточная загрузка — клиент получает ВСЕ поля, даже ненужные  
❌ Множественные запросы — чтобы собрать данные из разных ресурсов, нужно несколько запросов  
❌ Нет строгого контракта типов (JSON — слаботипизированный)  
❌ Плох для реалтайма (нет push)  

## REST vs GraphQL (кратко)

| Критерий | REST | GraphQL |
|----------|------|---------|
| Клиент получает | Фиксированную структуру | Только то, что запросил |
| Число запросов | Может быть много (N+1) | Один запрос на всё |
| Версионирование | /v1/, /v2/ | Эволюция схемы |
| Кэширование | Встроенное (HTTP cache) | Сложнее |
| Сложность сервера | Проще | Сложнее |
| Когда применять | Стандартные API, публичные | Сложные клиенты, агрегация |
